# 产品体验与平台边界

Ghostty Studio 的目标不是把两百多个配置键排列成一张表，而是让用户放心地完成一次
本地配置变更：知道自己正在编辑什么、理解哪些内容会受到影响、随时可以退出，并且在
Ghostty、配置文件或应用升级后仍有清晰的恢复路径。

这份文档同时约束产品、交互和工程实现。界面文案可以调整，但不能模糊这里定义的真实
能力和安全边界。

## 北极星体验

理想的一次使用应该是：

1. 打开应用后直接回到上次使用的配置和设置上下文，可以马上开始调整。
2. 只有首次选择、多个可写来源、缺少配置或需要恢复时，应用才暂停编辑并请用户决定。
3. 用自然语言、Ghostty 原始键名或分类找到设置；不支持编辑的项目会说明原因。
4. 所有调整先进入本地草稿。浏览其他设置不会丢失草稿，也不会悄悄写盘。
5. 视觉选项在相关位置提供模拟预览；Ghostty 校验和保存前 diff 才是事实依据。
6. 草稿经过检查后才可保存；保存中不能重复提交，过期的检查结果不能用于新草稿。
7. 外部编辑、版本不兼容或校验失败时，优先保留磁盘上的新内容，再帮助用户重新读取、
   保留仍兼容的草稿或从快照恢复。

## 用户旅程

### 1. 开始编辑

如果上次使用的配置仍然有效，应用直接打开它并恢复最近的设置分类。环境状态保持安静：
正常时只需让用户知道当前文件和 Ghostty 版本；真正影响编辑时，才在相关操作附近解释
问题并提供下一步。

只有 Ghostty `1.3.1`、`stable` 渠道、macOS 和受审计 schema hash 同时匹配时才进入可写
体验。任一条件不符，应用从首次加载起就是只读浏览，不先展示可修改控件再在保存时拒绝。

浏览器预览是明确的只读体验。它可以用于了解界面，但不能暗示已经读取或能够保存真实
配置。

### 2. 确认配置来源

macOS、XDG、include 和 dotfiles 工作流可能同时存在。只有无法沿用上次选择，或同时
发现多个可写候选时，才打开来源选择。来源选择器决定“本次写入哪个文件”，来源图帮助
理解加载顺序；在完整 merge/reset 语义实现前，两者都不能宣称已经计算出 Ghostty 的
最终生效值。

切换写入目标是一项有后果的操作。有草稿时必须先让用户选择继续留在当前文件，或明确
丢弃草稿后切换，不能静默迁移到另一个文件。

尚无任何默认配置时，用户可以创建后端签发的固定空白候选。这个流程只支持用户目录内
可无损表示的路径：先用当前 Ghostty 验证固定的 0 字节内容，显示原生确认，确认后重新
探测候选和版本契约，再以 no-follow、exclusive-create 和私有权限创建。若另一个默认层
同时出现，全部文件保留并进入冲突状态。创建后的完整验证失败时也保留空文件并重新探测；
便携 POSIX 接口无法原子地“比较 inode 后删除”，因此不能用看似安全的自动清理冒险删除
刚被外部程序替换的内容。

### 3. 探索与编辑

设置以用户能理解的名称为主，Ghostty 键名作为稳定的技术标识保留。搜索同时覆盖本地化
名称、摘要、原始键名和官方说明。高级设置仍可发现，但在没有经过审计的编辑器时保持
只读，并说明缺少的是行为契约，而不是让用户猜测界面出了故障。

精确匹配当前受审计契约时，可编辑范围是 30 个普通标量和背景图片专用编辑器；其余项目
继续作为参考内容。版本、渠道、平台或完整 schema hash 不匹配时，整个目录保持只读，
不按单个设置指纹猜测兼容性。

常用设置优先出现，完整目录仍可搜索和浏览。默认值、原始键名、来源和诊断属于详细信息，
不应压过当前任务；风险或兼容性提示只在确实影响当前选项时出现。清空一个已配置的标量
表示从当前编辑层移除该赋值，而不是写入一个含义不明的空值。

### 4. 草稿与模拟预览

草稿是一次明确的本地事务：第一次修改后才出现待保存提示，显示修改数量，并提供放弃和
检查入口。导航、搜索和打开辅助工具不应改变草稿；离开应用前必须提醒。

终端预览只在颜色、字体、间距、透明度、光标等相关设置中出现。它是确定性的 DOM 模拟器，
不运行 shell，不加载主题命令，也不等同于 Ghostty 的真实渲染。无法准确模拟的属性应标为
“未预览”，而不是展示看似精确的结果。

### 5. 检查与保存

“检查更改”把当前草稿复制成一个不可变请求，由后端生成准确 diff、诊断和一次性变更
令牌。用户在检查期间继续修改草稿时，旧结果必须作废；保存按钮只允许应用屏幕上正在
展示并且仍与当前草稿一致的结果。

检查结果同时冻结本次涉及的设置契约。运行时 schema 刷新、检查和保存由后端串行处理；
保存会在系统确认前后重新加载契约。只要受审设置发生变化，旧检查结果立即失效，用户需
重新检查。

保存流程需要持续反馈：检查中、等待系统确认、写入中、完成或失败。保存中关闭对话框、
重复提交和切换来源都应被禁用。成功消息要说明实际写入目标和快照；失败消息要告诉用户
原文件是否保持不变，以及下一步可以重试、重新读取还是恢复。

### 6. 冲突、恢复与升级

检测到外部编辑时，以磁盘为准，绝不覆盖较新的文件。应用重新读取实际内容，再把仍受
支持的标量草稿重新叠加到内存中，要求用户重新检查。无法安全确认写入结果时，即使文件
看起来已经改变，也不能报告成功。

快照是最后一道恢复能力，不是正常撤销的替代品。恢复前同样展示后端生成的 diff、执行
Ghostty 校验、要求系统确认，并拒绝覆盖恢复期间出现的更新。

## 交互原则

这些原则参考 Apple 的 Settings、Feedback、Onboarding 和 Progress 指南，WCAG 2.2，
以及 Nielsen Norman Group 的十项可用性启发式原则。

- **状态始终可见：** 启动、草稿、检查、写入、兼容性和恢复状态都在相关操作附近显示；
  不能只靠颜色表达成功或风险。
- **使用用户语言：** 先说“当前配置文件”“待保存更改”“重新读取”，再补充 revision、
  schema hash 等工程细节。
- **控制权属于用户：** 不自动写盘，不在导航时丢草稿，危险操作可取消；真正提交前有
  原生系统确认。
- **预防优于报错：** 不兼容或语义未知的设置默认只读；选择来源、恢复快照和应用 diff
  之前先解释范围。
- **错误可以恢复：** 错误信息包含发生了什么、数据是否安全、建议动作。主路径上提供
  重试或重新读取，不要求用户从日志中寻找办法。
- **渐进披露：** 编辑器先呈现当前任务；原始键名、来源图和诊断留给需要它们的人，但
  始终可达。选择和恢复流程只在对应条件出现时打断主路径。
- **一致并可学习：** 保存、取消、重试、恢复在不同对话框中使用一致的顺序、名称和状态。
- **无障碍是基线：** 键盘可以完成全部任务；焦点进入对话框并在关闭后返回触发器；状态
  变化通过 live region 通知；正文保持可读对比度，交互目标至少满足 WCAG 2.2 的
  24 × 24 CSS 像素下限，并优先使用更舒适的 32 像素以上目标。
- **尊重动态与注意力：** 不用闪烁表达状态，不在持续拖动时触发高成本全页面重绘，遵循
  `prefers-reduced-motion`，并避免没有完成条件的动画。

## 信息架构：编辑是默认，工具按需出现

产品由一个主要编辑流程和三组按需能力组成：

| 区域 | 用户获得什么 | 何时出现 |
|---|---|---|
| 设置编辑 | 常用设置、完整目录、搜索和上下文预览 | 默认打开；只有经过审计的类型可写 |
| 草稿与保存 | 未保存数量、人能读懂的变更摘要、准确 diff 和安全写入 | 产生修改后出现 |
| 来源与环境 | 配置选择、创建、加载顺序和诊断 | 首次选择、来源变化或用户主动查看时出现 |
| 兼容与恢复 | Ghostty 契约变化提示、冲突处理和快照恢复 | 发生升级、冲突或用户主动恢复时出现 |

扩展 manifest 目前只有后端校验和开发者文档，没有普通用户可进入的扩展区域。

## 信息可信度

界面必须让用户分辨以下三种信息，不能都称为“当前值”：

| 信息 | 当前来源 | 可以如何使用 |
|---|---|---|
| 当前编辑层中的值 | 后端打开的单个配置文档 | 可以形成草稿和准确 diff |
| 来源观察图 | 受限解析得到的加载节点与声明位置 | 用于排查，不代表完整 merge 结果 |
| 最终生效值 | 需要版本匹配的完整加载、reset 与重复值语义 | 当前尚未完整实现，必须明确标注未知 |

同样，模拟预览是反馈工具；保存候选是否有效由本机安装的 Ghostty 校验决定。

## Ghostty 升级兼容策略

当前唯一可写契约是 Ghostty `1.3.1` + `stable` + macOS + 精确 schema hash。已安装的
Ghostty 二进制及其原始 `+show-config --default --docs` 输出共同决定是否匹配；上游输出中的
尾随空格也是 hash 的一部分。

- 新增、移除或改写文档内容都会改变完整 hash，并让目录从加载起只读。
- 渠道、平台或版本不匹配同样关闭全部写入，不按单个设置指纹放行。
- 保存和恢复前再次探测 Ghostty 与 schema；检查结果只对当时冻结的设置契约有效。
- 真实离线 fixture 和 expected contract 用于发现上游漂移，但不替代本机保存前校验。

未来如需减少无关上游变化造成的只读范围，必须先建立新的、独立审计的逐设置授权模型；
当前版本不会推测兼容。

升级恢复流程遵循：发现变化 → 展示摘要 → 只读保留未知内容和本地草稿 → 重新解析来源。
只有恢复精确受审契约后，草稿才可重新检查；当前不迁移或推测放行。

## 扩展契约与安全模型

默认扩展是严格 JSON 数据，不是在 WebView 或应用进程内执行的插件。每个 manifest 声明
自身版本、host API 要求、Ghostty 版本范围、请求能力和贡献内容；未知字段、未知能力、
超限内容和版本不兼容都会被拒绝。

当前实现只保留 Rust 内部的静态校验和开发者契约，不向 renderer 暴露 IPC，也没有扩展
浏览、安装、管理或执行入口。完整格式与限制见 [扩展设计](EXTENSIONS.md)。

未来的安装生命周期至少包括：来源与完整性摘要、权限说明、用户确认、隔离存储、启用/
停用、版本固定、兼容性复检、升级回滚和卸载。第三方扩展不能读取配置文件、联网、启动
进程或调用任意 Tauri IPC。只有本地明确信任且完整性固定的包，才可能覆盖核心行为
metadata。

如果将来出现声明式数据无法满足的真实场景，应先评估独立进程或 WASI 沙箱：默认无
网络和文件访问，限制 CPU、内存与响应大小，通过版本化协议通信。这是独立的高风险产品
能力，不能成为普通扩展的隐式升级路径。

## 当前能力与明确限制

当前代码已经具备动态设置目录、配置候选发现、独立草稿、上下文预览、后端 diff、Ghostty
校验、外部 revision 检查、原子写入和本地快照等纵向能力。通常打开即进入设置编辑；来源
选择、兼容提示和恢复只在需要决策时出现。无默认配置时还支持受限的 0 字节安全创建事务。
扩展清单检查目前仅作为后端和开发者契约存在，不属于普通用户旅程。

仍然属于部分能力或后续阶段的内容：

- 完整的最终生效值与 reset/repeatable merge 引擎；
- 主题、快捷键、多值、路径和敏感设置的专用编辑器；
- 托管 overlay、raw 专家模式和统一恢复中心；
- 扩展安装、信任库、签名、执行预设或迁移；
- 更多 Ghostty 版本的 fixture 与经审计写入契约；
- Developer ID 签名、公证、安全更新器和 Linux 正式支持；
- 完整国际化与经过辅助技术验证的无障碍审计。

在这些能力完成前，界面和文档都不应提前承诺。

## 体验验收场景

每个发布版本至少人工或自动覆盖以下旅程：

1. 正常启动直接进入上次的编辑上下文；无 Ghostty、无配置文件、只读配置、多个候选和
   浏览器预览分别进入可理解的按需状态。
2. 只用键盘完成搜索、修改、撤销、检查、取消和保存，关闭对话框后焦点返回合理位置。
3. 检查请求尚未完成时继续拖动滑块，旧结果不会覆盖新草稿，页面不闪烁或跳动。
4. 保存前由外部编辑器改变文件，外部内容不丢失，兼容草稿仍可重新检查。
5. Ghostty 在会话期间升级或 schema 改变，写入关闭并出现可执行的恢复说明。
6. 完整来源图不可用时，界面不再把编辑层值冒充最终生效值。
7. 恶意、超大、未知能力或版本不兼容的扩展清单被拒绝，且不会写盘或访问网络。
8. 从快照恢复时发生新的外部编辑，应用拒绝覆盖并解释磁盘状态。

Ghostty Studio 默认不收集遥测。体验质量通过本地测试、脱敏问题报告、可复现 fixture 和
有明确任务的可用性测试改进，而不是以采集真实配置为代价。
