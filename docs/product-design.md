# Ghostty Studio 产品设计准则

Ghostty Studio 帮助用户安全地理解和调整 Ghostty 配置。它不是配置键的展示页，也不把
规范名称搬进界面；它应当让人清楚地知道自己在改什么、何时会生效、出现问题后如何返回。

本文件记录产品长期遵循的设计基线。更完整的用户旅程与安全边界见
[产品体验与平台边界](PRODUCT_EXPERIENCE.md)。

## 规范矩阵

| 类型 | 采用规范 | 在产品中的作用 |
| --- | --- | --- |
| 总体交互思想 | [Nielsen 十大可用性原则](https://www.nngroup.com/articles/ten-usability-heuristics/) | 判断状态是否清楚、操作是否可控、错误是否可恢复、信息是否恰到好处 |
| macOS 平台行为 | [Apple Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/) | 指导窗口、菜单、焦点、键盘、设置入口与系统偏好适配 |
| Windows 平台行为 | [Windows App Design Guidelines](https://learn.microsoft.com/windows/apps/design/) | 指导导航、设置页、键盘、高对比度与 Windows 平台习惯 |
| Linux / 专业桌面思想 | [KDE Human Interface Guidelines](https://develop.kde.org/hig/) | 指导高信息密度桌面布局、响应式侧栏、系统主题和专业用户效率 |
| 无障碍 | [WCAG 2.2 AA](https://www.w3.org/TR/WCAG22/) | 提供可测试的对比度、重排、键盘、焦点、目标尺寸和状态通知底线 |
| Qt 实现参考 | [Qt Quick Controls](https://doc.qt.io/qt-6/qtquickcontrols-index.html) | 提供控件选择、平台样式、键盘和无障碍语义参考 |
| 内部视觉统一 | Ghostty Studio Desktop Design System | 统一信息层级、间距、排版、色彩、组件状态与响应式行为 |

这些规范不是平行堆叠的清单。发生冲突时按以下顺序判断：

1. **WCAG 2.2 AA 是不可降低的底线。** 视觉偏好不能覆盖键盘、对比度、重排或辅助技术要求。
2. **当前操作系统的行为习惯优先。** 快捷键、窗口、焦点、按钮顺序和系统设置应符合用户
   正在使用的平台，而不是把 macOS、Windows 与 KDE 的外观混在一起。
3. **Nielsen 原则约束完整旅程。** 平台规范没有回答的问题，以可见状态、用户控制、预防
   错误、识别优于记忆和渐进披露为判断依据。
4. **内部设计系统统一品牌与结构。** 它负责共同的排版、间距和组件状态，但不抹平平台行为。
5. **实现框架服务于以上目标。** 不能为了复刻某个控件的外观而牺牲语义、性能或可访问性。

## Qt 与当前架构的边界

当前应用由 Tauri、React 和 Rust 构建，不是 Qt 应用。现阶段采用 Qt Quick Controls 的是
控件选择与交互语义，例如：

- 两态设置使用开关或复选框；
- 少量互斥选择使用单选按钮，选项较多时使用下拉选择；
- 有明确范围、强调快速调整的数值使用滑块；需要精确输入时同时提供数值输入；
- 标准控件必须具备键盘、焦点、名称、角色和值。

React 界面使用语义化 HTML 和平台能力实现这些原则。项目文档、发布说明和产品界面不能
声称当前版本“使用 Qt 实现”或“符合 Qt 原生外观”。如果未来决定迁移到 Qt Quick，必须
单独评估插件生态、WebView 安全边界、打包体积、跨平台维护成本和迁移路径，并记录新的
架构决策，不能在日常视觉迭代中悄悄替换技术栈。

Qt 自带的 macOS、Windows 和 Linux 样式说明了一个重要方向：平台原生感来自系统行为与
控件反馈，不是给所有系统套上同一套仿原生皮肤。参考
[Qt Quick Controls 样式](https://doc.qt.io/qt-6/qtquickcontrols-styles.html)和
[Qt Quick 无障碍](https://doc.qt.io/qt-6/accessible-qtquick.html)。

## 产品原则

### 从任务开始

打开应用后，用户应尽快到达可编辑的配置。只有配置来源无法判断、文件不可写、存在重复
设置或版本不兼容时，才中断主流程并请求决定。

### 先给结果，再给原理

名称和说明先回答“这会改变什么”。Ghostty 原始键名、来源、默认值和官方长说明保留在
详情中，供需要核对的人查看。

### 可见但不过度提醒

当前配置、Ghostty 版本、草稿数量、写入状态和生效方式应随时可确认。正常状态保持安静；
只有影响当前操作的信息才提升视觉权重。

### 预防错误，并保留退路

视觉预览可以即时更新，但写入外部配置文件必须经过检查和明确保存。应用提供放弃草稿、
重新读取、快照恢复和清楚的失败说明。这里有意不采用普通设置页常见的即时写盘，因为
Ghostty Studio 修改的是用户可能手工维护、被多个工具共享的文件。

### 复杂能力按需出现

主页面优先呈现真正可调整的设置。尚无安全编辑器的项目使用静态参考卡片，说明当前状态
和可行的下一步；不放置看起来损坏的禁用输入框。来源图、原始键名和诊断保持可达，但不
抢占主任务。

### 每个状态都能行动

不要只说“不可用”“不兼容”或“发生错误”。说明原因，并在存在安全方案时提供一个明确
动作，例如“更新 Ghostty”“选择其他配置文件”“保留一个重复值”或“重新读取”。

## 双语体验

### 语言模型

应用支持三种偏好：

```text
system | zh-Hans | en
```

界面显示为：

| 当前界面 | 系统 | 简体中文 | English |
| --- | --- | --- | --- |
| 简体中文 | 跟随系统 | 简体中文 | English |
| English | Use system setting | 简体中文 | English |

- 首次启动跟随系统；用户作出的明确选择持久保存。
- 切换立即生效，不刷新页面，不丢失草稿、搜索、分类、滚动位置、对话框状态或键盘焦点。
- 只有处于“跟随系统”时，应用才响应操作系统语言变化。
- 语言选择使用文字，不用国旗；旗帜代表国家，无法准确代表语言。
- WebView 根元素同步使用 `lang="zh-Hans"` 或 `lang="en"`。以后支持从右向左的语言时，
  同时切换阅读方向和方向性图标。
- 语言与地区分开处理。界面语言不能被用来猜测日期、数字或地区偏好。

语言控件放在始终可找到的工具区，宽屏位于顶部右侧并保持较低视觉权重；窄窗口移入导航
菜单。位置可以响应式变化，但名称、图标和当前状态必须一致。

参考：[Apple 本地化](https://developer.apple.com/localization/)、
[Windows 全球化与本地化](https://learn.microsoft.com/windows/apps/design/globalizing/globalizing-portal)和
[W3C 语言声明](https://www.w3.org/International/docs/bp-html-lang/)。

### 内容结构

每条用户可见内容使用稳定的语义标识，不使用中文或英文原句作为程序键。设置文案至少包含：

```text
label          设置名称
summary        必要时显示的一行说明
choiceLabels   选项的本地化名称
status         当前状态与生效方式
searchAliases  本地化名称和常见搜索词
```

Ghostty 配置键和值属于文件格式，不翻译。例如界面可以显示“覆盖 / Cover”，但写入值仍是
`cover`；`background-opacity` 作为次级代码标识保留。搜索同时索引当前语言、另一种语言、
原始键名和常见别名，切换语言后仍能找到同一个设置。

所有内容必须进入同一套语言系统，包括导航、按钮、占位文字、选项、空状态、错误、保存
结果、对话框、通知、无障碍名称和原生菜单。不能只翻译页面主体。

### 中文文案

- 使用自然、直接、克制的现代书面语。
- 名称优先描述结果，例如“鼠标移入时聚焦”，不用语义颠倒的“鼠标跟随焦点”。
- 说明通常只写一句；先写效果，确有必要时再写限制。
- 避免翻译腔和内部词汇，例如“能力暴露”“运行时契约”“写入语义”“Schema 漂移”。
- 使用“无法保存到此文件”“需要 Ghostty 1.4 或更高版本”“发现两处相同设置”等用户能
  理解的表达。
- 布尔设置描述开启后的正向结果，避免双重否定。

### 英文文案

- Use plain, direct, neutral language.
- Use sentence case for setting labels and descriptions.
- Begin action labels with a specific verb: “Review changes”, “Choose config”, “Reload file”.
- Prefer positive phrasing and avoid implementation jargon.
- Keep labels parallel within a choice group and place shared wording in the group label.
- Use complete sentences only where a sentence adds useful context.

中英文都遵循同一信息层级，但不是逐字互译。译文应像该语言中的原生产品文案。配置项的
首要目标是准确；不能为了口语化改变数值方向或实际含义。

参考：[Apple Writing](https://developer.apple.com/design/human-interface-guidelines/writing)、
[Windows UI text](https://learn.microsoft.com/windows/win32/uxguide/text-ui)和
[KDE Text and labels](https://develop.kde.org/hig/text_and_labels/)。

## 轻量 Desktop Design System

内部设计系统保持小而稳定。组件只能使用语义 token，不在单个页面创造相近但不同的尺寸
或颜色。

### 间距与尺寸

| Token | 值 | 用途 |
| --- | --- | --- |
| `space-1` | 4 px | 图标内部、紧密辅助信息 |
| `space-2` | 8 px | 同一控件内元素、相邻按钮 |
| `space-3` | 12 px | 标签与说明、相关控件 |
| `space-4` | 16 px | 设置行内边距、卡片内容 |
| `space-6` | 24 px | 设置分组、页面区块 |
| `space-8` | 32 px | 主要章节与宽屏留白 |
| `control-min` | 32 px | 桌面标准控件高度 |
| `target-comfortable` | 36 px | 主要按钮、图标按钮和紧密交互的推荐点击范围 |

WCAG 2.2 AA 的指针目标下限是 24 × 24 CSS px；32–36 px 是产品目标，不用下限作为默认
尺寸。圆角只保留小、中、大三个层级，分别服务输入控件、内容表面和主要浮层。

Ghostty Studio 的标准表单控件和图标按钮统一为 32 px，分段按钮与披露控件使用 28 px。
开关保留 44 × 32 px 的命中区域，内部轨道为 36 × 20 px。不要再用 `min-height` 为不同
尺寸的控件打补丁；组件必须明确属于标准、紧凑或图标按钮三档之一。

### 排版

- 正文基准为 14 px，默认行高不低于 1.5。
- 设置名称使用 14–15 px、半粗字重；说明使用正常字重和次级颜色。
- 页面标题、分组标题、设置名称、说明、元信息最多形成五个清楚层级。
- 说明文字默认不超过约 52 个字符宽；需要更多内容时进入详情，而不是无限拉宽行。
- 不用全大写、连续粗体或过多字号制造层级。
- 使用系统字体栈，尊重系统字号、缩放和文字渲染。

### 色彩与状态

- 品牌绿色用于当前选择、主要操作和成功确认，不用于大面积装饰。
- 错误、警告、成功和信息都同时使用文字或图标，不能只靠颜色。
- 正文与背景对比度至少 4.5:1；大号文字至少 3:1；控件边界、图标和焦点至少 3:1。
- hover、active、focus、selected 和 disabled 必须可区分。焦点不能仅复用 hover 效果。
- 只读参考不是 disabled 控件状态；它有自己的静态卡片和可理解状态。

### 设置行

标准设置行按以下顺序组织：

1. 用户能理解的名称；
2. 必要时的一行说明；
3. 当前值或编辑控件；
4. 仅在需要时显示的平台、版本或生效提示；
5. 展开后显示 Ghostty 键名、默认值和官方说明。

宽屏时文字位于左侧，控件在稳定的右侧列中与标题顶部对齐；展开详情不能移动控件。右侧
明确分成“主控件 + 32 px 撤销操作”两列。窄屏时改为上下排列，控件获得完整宽度。静态
参考卡片不进入键盘顺序，只有其中真正可操作的链接或按钮可聚焦。

### 控件选择

- 明确的两态设置使用开关；需要组成多选集合时使用复选框。
- 3 个以内、文字较短的互斥选项优先使用单选按钮；4–10 个选项使用下拉选择。
- 有范围且强调快速探索的数值使用滑块；强调精确值时使用数值输入。
- 同时提供滑块和数值输入时，两者共享一个值、一个名称和一致的步进与边界。
- 色块、十六进制前缀与色值属于一个组合控件；语言图标和语言选择也属于一个组合控件。
- 数值控件显示用户需要理解的单位，并使用等宽数字，避免数值变化时宽度抖动。
- 按钮执行动作，不用按钮表达持续状态；按钮名称使用具体动词。
- 图标按钮必须有可见提示和无障碍名称，不能要求用户猜图标。

参考：[Qt Quick Controls 使用指南](https://doc.qt.io/qt-6/qtquickcontrols-guidelines.html)、
[KDE Getting input](https://develop.kde.org/hig/getting_input/)和
[Windows Settings](https://learn.microsoft.com/windows/apps/design/app-settings/guidelines-for-app-settings)。

### 动效

- 动效只解释状态变化，不作为装饰性的持续反馈。
- 拖动滑块时只更新必要区域，不能触发窗口尺寸、主要网格或整页高成本重排。
- 避免闪烁、反复发光和没有完成条件的动画。
- 遵循系统“减少动态效果”设置；在该模式下使用即时状态变化。

## 桌面布局与响应式行为

布局优先保证任务连续性，不追求在每个宽度维持相同列数。

| 可用宽度 | 布局 |
| --- | --- |
| 1151 px 及以上 | 导航、设置、上下文预览三栏同时可见 |
| 780–1150 px | 保留导航与设置；预览改为设置区内的按需披露；工具栏隐藏次要文字 |
| 520–779 px（浏览器预览） | 设置控件改为上下排列；导航保持紧凑；操作区允许换行 |
| 低于 520 px 或高倍率缩放 | 单栏阅读顺序；弹窗与操作区使用完整可用宽度 |

- 页面只有一个主要纵向滚动区。弹窗和短列表可以独立滚动，但不能制造难以控制的嵌套滚动。
- 搜索和当前上下文可以保持可见，但吸顶内容不能遮住键盘焦点。
- 宽屏内容限制可读宽度；设置说明不因窗口拉宽变成长行。
- 中文、英文、200% 字体缩放和约 50% 的伪本地化文字增长都不能造成截断或控件重叠。
- 在等效 320 CSS px 宽度下，除确实需要二维结构的内容外，不得要求横向与纵向同时滚动。
- 方向、边距和对齐使用逻辑起点与终点，为未来从右向左的语言保留空间。

参考：[Apple Layout](https://developer.apple.com/design/human-interface-guidelines/layout)、
[Windows content layout](https://learn.microsoft.com/windows/apps/design/basics/content-basics)、
[KDE Layout and navigation](https://develop.kde.org/hig/layout_and_nav/)和
[Qt 响应式布局](https://doc.qt.io/qt-6/qtquicklayouts-responsive.html)。

## 键盘、焦点与辅助技术

完整主流程必须能在不使用鼠标的情况下完成。

- Tab 顺序与视觉和阅读顺序一致；不可操作内容不进入 Tab 顺序。
- 方向键用于侧栏、单选组、组合控件与滑块内部导航。
- Enter 或空格执行当前控件的标准动作。
- Escape 关闭菜单、弹层或对话框；关闭后焦点返回原触发位置。
- 对话框打开后将焦点放到标题、首个需要处理的字段或最合理的安全动作，并限制焦点在
  对话框内。
- macOS 提供 `Command–,` 打开设置；其他快捷键遵循当前平台，不占用系统级组合键。
- 搜索、检查更改、保存和关闭等高频动作可以有快捷键，并在菜单或提示中发现。
- 所有控件具有可被辅助技术读取的名称、角色、状态和值。可见标签应出现在无障碍名称开头。
- 草稿数量、验证结果、写入成功和失败通过礼貌的状态通知发布，不抢夺当前焦点。
- 焦点指示始终可见，与相邻颜色至少达到 3:1，且不被工具栏、预览或底部操作条完全遮挡。
- tooltip 只能补充信息，不能承载完成任务所必需的唯一说明。

参考：[Apple Keyboards](https://developer.apple.com/design/human-interface-guidelines/keyboards)、
[Windows Keyboard interactions](https://learn.microsoft.com/windows/apps/develop/input/keyboard-interactions)和
[WCAG 2.2 可操作性要求](https://www.w3.org/TR/WCAG22/#operable)。

## 跨平台行为

| 方面 | macOS | Windows | Linux / KDE |
| --- | --- | --- | --- |
| 设置入口 | App 菜单与 `Command–,` | 稳定的导航入口，遵循 Windows 导航习惯 | 菜单或稳定导航入口，遵循桌面环境习惯 |
| 外观 | 尊重强调色、深浅模式、减少动态效果 | 尊重系统主题、高对比度与缩放 | 尊重系统字体、配色、图标主题与动画设置 |
| 键盘 | Command 系列标准快捷键与清楚焦点环 | 完整 Tab、方向键、快捷键和访问键 | 无鼠标完成全部操作，使用标准桌面快捷键 |
| 窗口 | 恢复最近分类和合适窗口尺寸 | 适应贴靠、缩放与多种窗口尺寸 | 适应平铺、小窗口和不同桌面主题 |
| 安装发布 | 签名、公证与系统安全提示准确 | 签名、安装来源与卸载路径准确 | 明确包格式、桌面集成和依赖范围 |

平台适配不得改变数据安全承诺：任何系统上都不能静默覆盖外部编辑、跳过检查或在界面中
声称模拟预览等同于 Ghostty 的最终渲染。

## WCAG 2.2 AA 发布基线

每次发布至少验证以下项目：

- 正文对比度达到 4.5:1；大字、图标、控件边界和焦点达到对应的 3:1 要求。
- 信息不只依赖颜色、位置、形状、动画或声音。
- 200% 文字缩放不丢失内容或功能；高倍率缩放下页面可重排。
- 所有功能可使用键盘，无焦点陷阱，焦点顺序合理且始终可见。
